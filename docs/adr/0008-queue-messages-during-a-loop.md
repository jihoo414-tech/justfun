# 루프가 도는 중에 온 메시지는 대기열에 두고, 화면은 폴링으로 답을 받는다

한 대화방에서는 루프가 한 번에 하나만 돈다. 처음에는 루프가 도는 중에 온 메시지를 409("아직 답하는 중이에요")로 거절하고 입력창을 잠그기로 했지만, 사용자 경험이 나빠서 바꿨다.

이제 그 메시지는 저장만 해 두고, 지금 루프가 끝나면 쌓인 메시지를 모두 넣어 루프를 한 번 더 돌린다. 예를 들어 "금요일 저녁 비어 있어?" 뒤에 "아 토요일도"가 오면 금요일 답이 나온 뒤 토요일까지 이어서 답한다. LangGraph 에이전트 서버의 기본값(enqueue)과 Claude Code처럼, 도구를 쓰며 오래 일하는 에이전트에서는 대기열이 흔한 방식이다.

메시지를 보내는 요청이 답을 기다렸다가 돌려받는 동기 방식으로는 두 번째 메시지의 답을 돌려줄 길이 없다. 그래서 화면과 Spring 사이는 메시지를 보내면 `202 Accepted`를 받고, "생각 중"인 동안 새 메시지를 폴링하는 방식으로 바꾼다. Spring과 Python 사이는 동기 HTTP 그대로다.

## Considered Options

- **거절 (409 + 입력창 잠금)**: 가장 단순하지만, 사용자가 덧붙이고 싶은 말을 답이 끝날 때까지 들고 있어야 한다.
- **메시지마다 따로 답하기**: 구현은 대기열과 거의 같지만, 첫 답이 이미 낡은 내용이 되기 쉽고 호출이 메시지 수만큼 든다.
- **하던 루프를 취소하고 새로 시작 (rollback)**: 최신 의도만 반영되지만, 이미 만든 승인 카드가 남아 상태가 헷갈리고 비용이 낭비된다.
- **도는 루프에 새 메시지를 끼워 넣기 (steer)**: 가장 자연스럽지만, Python이 도구를 부를 때마다 새 메시지를 확인해야 해서 상태 없는 Python 설계가 복잡해진다. v2 후보로 둔다. [중지] 버튼도 v2 후보다.

## Consequences

- 루프 잠금은 `conversations.loop_locked_until`(잠금 만료 시각)로 둔다. 비었거나 지난 시각일 때만 조건부 UPDATE로 잡으므로, 서버가 루프 도중 죽어도 그 시각이 지나면 저절로 풀린다. 사용자에게는 보이지 않는다.
- 실행 기록에 그 루프에 넣은 마지막 사용자 메시지(`agent_runs.last_message_id`)를 남기고, 루프가 끝나면 그보다 새 메시지가 있는지 확인한다.
- 루프는 메시지 요청 스레드가 아니라 백그라운드에서 돈다. 화면과 Spring 사이의 긴 타임아웃이 필요 없어진다.
- 웹 채팅으로 가는 브리핑도 같은 잠금을 잡고 메시지를 올린다.
- 대기열 때문에 도는 루프도 하루 상한에 하나로 센다.
